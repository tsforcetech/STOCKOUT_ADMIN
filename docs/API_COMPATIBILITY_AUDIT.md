# API compatibility audit — admin console vs. .NET backend

Audited: 2026-10-18 against `/home/user/stockout` at commit `7a1f4bc` (the only commit in the checkout, newer than `docs/contracts/*`). Every endpoint was re-verified against the C# controllers, DTOs, services and SQL procedures; the contract docs were not trusted.

**Scope.** Every HTTP call in `src/services/*.ts` (10 modules). `grep -rnE "http\.(get|post|put|patch|delete|request)" src` finds no direct `http.` use outside `src/services` except the HTTP client's own tests, and nothing calls `fetch` except `src/lib/api/client.ts`. There are 145 distinct method + path pairs. `inspectionsService.template` is the same endpoint as `inspectionTemplatesService.get`, so it has one row.

**Common checks that apply to every row (not repeated per row):**

- **Gateway.** Every path matches a route in `gateways/Emcore.ApiGateway/appsettings.json`, and the gateway forwards it unchanged with no transforms. Admin, platform, user, identity and file routes use `AuthenticatedRoutePolicy`, which also validates the session (`Extensions/GatewayExtensions.cs:250-290`). `/api/v1/auth/*` uses `PublicPolicy` with the 10 requests/min/path `LoginOtpPolicy` (`Extensions/GatewayExtensions.cs:143-153`, `appsettings.json:43-48`). On those routes the identity service enforces `[Authorize]` itself.
- **Envelopes.** The four services wrap responses differently. The UI uses the matching adapter for each:
  - identity-access returns bare DTOs and ProblemDetails errors (`BaseApiController.MapResult`).
  - user-organization returns `{success,data}` (`Contracts/Responses/ApiResponse.cs:3`, `BaseApiController.cs` MapResult). Errors are `{error,message}` or ProblemDetails.
  - catalog-listing taxonomy returns `{success,data}` (`Contracts/Responses/ApiResponse.cs:3`). Its moderation, inspections and templates endpoints return bare DTOs, and their errors are `{error,message}` (`Api/Filters/MarketplaceExceptionFilterAttribute.cs`).
  - inventory-media returns `{data}`, and errors are `{errorCode,message}`.
  - notification-integration returns `{success,data}` (`EnvelopeResponse`), and errors are `{error,message}`.

  `unwrapData` accepts only `{success?,data,message?}`, and `parseErrorBody` reads `error`, `errorCode` and `code`.
- **JSON.** No service registers `AddJsonOptions` or a `JsonStringEnumConverter`, so JSON uses camelCase and all enum-like values are plain strings. Every key the UI sends exists on the C# request type, with a compatible type.
- **Error codes.** Every error code the UI branches on or maps to a message exists in the backend. That covers `features/catalog/lib/errors.ts`, `features/team/errors.ts`, `features/listings/shared.tsx` HINTS, `features/notifications/template-rules.ts`, `hasErrorCode(...)` and `e.code === ...`. Each code was grepped in the C# and SQL of its service: all `MARKETPLACE_*` and taxonomy codes in catalog-listing, `TEMPLATE_*` and `NOTIFICATION_TEMPLATE_NOT_FOUND` in notification-integration, and the user-organization codes in its controllers.
- **Permissions.** The permission codes the UI gates on match the `RequiresPlatformPermission` attributes and `HasPermissionAsync` calls exactly. user-organization compares codes case-insensitively (`Application/Services/PlatformPermissionService.cs:32-35`), and the UI lower-cases them.

## Fixes made

1. **The file upload policy was wrong for three purposes, and file extensions were never checked** (`src/services/files.service.ts`).
   - **Backend policy.** inventory-media accepts an upload only when the lower-cased MIME type **and** the `Path.GetExtension` extension are both in the purpose's allow-list, and the size is between 1 byte and the maximum (`inventory-media/src/Emcore.InventoryMedia.Application/Services/FileAssetService.cs:30-39,55-60`).
   - **What the UI had wrong.**
     - It allowed `*/*` for `CHAT_ATTACHMENT` and `GENERAL_ATTACHMENT`. The backend allows only pdf, jpeg, png and webp.
     - It left `image/webp` out of `RETURN_EVIDENCE`.
     - It checked neither the extension nor a zero-byte size, so files such as `photo.jfif` (`image/jpeg`) or a PNG with no extension failed only after the round-trip, with `FILE_CONTENT_TYPE_INVALID`.
   - **Fix.**
     - `FILE_LIMITS` now matches the server policy exactly and adds `extensions`.
     - A new `isAllowedFileType()` helper applies the server's MIME + extension rule.
     - `filesService.upload()` checks the extension and a zero-byte size before calling the API.
     - `features/account/profile-photo.tsx` and `features/inspections/detail/evidence.tsx` use the helper when a file is picked.
     - Added `src/services/__tests__/files.service.test.ts`.
2. **Date-range upper bounds dropped the last second of the selected day** (`src/features/listings/shared.tsx` `dateInputToUtc`, `src/features/account/activity-card.tsx`).
   - **Backend.** The procedures compare inclusively:
     - `i.CreatedAtUtc <= @DateTo` (`catalog-listing/Emcore.CatalogListing.Migrator/Migrations/Versioned/034_Stage5E_InspectionProcedures.sql:268`)
     - `v.UpdatedAtUtc <= @SubmittedToUtc` (`…/036_Stage5F_ModerationPublicationProcedures.sql:637`)
     - `OccurredAtUtc <= @ToUtc` (`identity-access/Emcore.IdentityAccess.Migrator/Migrations/Versioned/016_Add_Account_Activity_Tracking.sql:59`)
   - **Bug.** The UI sent `YYYY-MM-DDT23:59:59Z`, which excluded rows stamped `23:59:59.001–.9999999`.
   - **Fix.** The UI now sends `T23:59:59.9999999Z`. This affects:
     - the inspections queue `dateTo`
     - the moderation queue `submittedToUtc`
     - account activity `toUtc`
3. **A seeded permission code was missing** (`src/api/types/user-organization.ts` `PERMISSIONS`). `catalog:search:admin` is seeded by `user-organization/Emcore.UserOrganization.Migrator/Migrations/Versioned/028_Stage6F_SearchAdminPermissions.sql:12` but was absent from `PERMISSIONS`. It is added as `CATALOG_SEARCH_ADMIN`. No screen uses it yet.

Apart from these, every request, query and response contract matched the current backend.

## Backend issues (not fixable in UI)

These defects still exist at the audited commit. The UI behaves correctly against the actual behaviour and explains each one where it matters.

1. **Identity admin status change has no authorization.** `PUT /api/v1/identity/admin/users/{id}/status` and `POST …/status` check only `[Authorize]`; neither the controller nor the service checks a permission.
   - Controller: `identity-access/src/Emcore.IdentityAccess.Api/Controllers/AdminController.cs:12-49`
   - Service: `Application/Commands/Handlers.cs:1332-1362`

   Any signed-in user can lock, suspend or close any account. The UI's `platform-users.disable` gate restricts only the console itself.
2. **Saving inspection responses persists nothing.** `PUT …/inspections/{id}/responses` writes no answers.
   - Cause: the service serializes `request.Responses` with default (PascalCase) `JsonSerializer` options (`catalog-listing/src/Emcore.CatalogListing.Application/Inspections/ListingInspectionService.cs:388`). The procedure reads camelCase paths such as `'$.inspectionResponseId'` (`034_Stage5E_InspectionProcedures.sql:707-711`), and `OPENJSON` paths are case-sensitive.
   - Effect: the endpoint returns 200, but completing an inspection whose template has required items fails with `MARKETPLACE_INSPECTION_CHECKLIST_INCOMPLETE`.
   - UI: `features/inspections/detail/checklist.tsx` compares the returned responses and warns when nothing was stored.
3. **Saving a non-empty category unit list always fails.** `PUT …/categories/{id}/units` with a non-empty `units` array returns 404 `UNIT_NOT_FOUND`.
   - Cause: the same casing bug. `CategoryUnitService.cs:62` serializes PascalCase JSON, while `Catalog_CategoryUnit_ReplaceDirect` reads `'$.unitId'` (`019_CategoryUnit_Procedures_Remediation.sql` and `016_…`).
   - UI: `category-units-tab.tsx` explains this failure.
4. **Platform user role names are always empty.** `/platform/users` and `/platform/users/{id}` return `roles[].code` and `roles[].name` as `""`.
   - Cause: `PR_PLATFORM_USER_LIST` and `PR_PLATFORM_USER_GET` emit lower-case JSON keys (`011_Procedures_PlatformUsersAndInvitations.sql:484,510`). `PlatformUserRepository.cs:43,67` deserializes them case-sensitively into `PlatformUserRoleModel`.
   - UI: it never uses these values. It reads super-admin roles through `/platform/admins/{id}/roles`, and the role editor warns that it starts empty.
5. **`POST /api/v1/auth/logout` revokes nothing.** It calls `RevokeSessionAsync(hash(refreshToken), …)`, passing a token hash where a session id is expected (`Handlers.cs:694-697`). The UI revokes the JWT `sid` session through `DELETE /auth/sessions/{sid}` instead.
6. **Files are owner-scoped.** `download-url` returns 403 `FILE_ACCESS_DENIED` for any file the admin did not upload (`FileAssetService.cs:205`). This includes seller listing media and documents, so admins cannot open them. The UI shows "not downloadable".
7. **Some user-organization errors carry no machine code.** Errors that go through `MapResult` are plain ProblemDetails, so the internal `Error.Code` is lost (`user-organization/src/Emcore.UserOrganization.Api/Controllers/BaseApiController.cs` MapResult). This affects:
   - `/platform/admins/*`
   - `/admin/marketplace/sellers/*` writes
   - `/users/me`

   For example, the last-super-admin conflict on `DELETE /platform/admins/{id}/roles/{code}` can only be recognised from its `detail` text (`PlatformAdminService.cs:94`).
8. **Timestamp precision is lost on date filters.** The repositories pass `DateTime` filters through Dapper without `AddTypeMap(DateTime, DbType.DateTime2)` (none in the repo), so they reach SQL Server as legacy `datetime` (≈3 ms precision). The new end-of-day bound `23:59:59.9999999` therefore rounds to the next midnight. In effect the filter is `<= next-day 00:00:00.000`, which can include only rows stamped at exactly midnight.
